DocuMentor Documentation

DocuMentor is an AI-powered documentation assistant that helps developers search and understand programming documentation through natural language questions. It uses Retrieval-Augmented Generation (RAG) to fetch relevant documentation chunks and generate accurate, cited answers.

This document covers every component of the system in detail. After reading it, you should be able to understand how data flows from raw documentation files all the way to a generated answer on the user's screen.

Two ways to interact:
  • Web UI — Next.js frontend at http://localhost:3000 (Dashboard + Q&A pages)
  • REST API — FastAPI backend at http://localhost:8100 (all endpoints available programmatically)

What is RAG? (Retrieval-Augmented Generation)

Before diving into the code, let's understand the core concept. RAG is a technique that combines a search engine with a language model. Instead of relying solely on the LLM's training data, RAG first retrieves relevant text from a knowledge base, then augments the LLM prompt with that text so it can generate an accurate, grounded answer.

Why RAG?

  • Accuracy — Answers are backed by actual documentation, not hallucinated facts
  • Citations — Every answer includes the source chunks that informed it
  • Up-to-date — Knowledge base can be updated without retraining the LLM
  • Domain-specific — Works with any documentation you ingest

RAG in DocuMentor (3 Phases)

Phase 1: INGESTION (one-time, per documentation source) ═══════════════════════════════════════════════════════ Raw Docs ──▶ Document Processor ──▶ Smart Chunker ──▶ Embeddings ──▶ ChromaDB (files, (extract text, (split into (384-dim (persistent URLs, clean HTML, ~500 token vectors) vector JSON) detect code) chunks) database) Phase 2: RETRIEVAL (every time a user asks a question) ═══════════════════════════════════════════════════════ User Question ──▶ Embed Query ──▶ ChromaDB Search ──▶ Top-K Chunks (same model) (cosine similarity) (most relevant) Phase 3: GENERATION (producing the final answer) ═══════════════════════════════════════════════════════ System Prompt + Retrieved Chunks + User Question ──▶ LLM ──▶ Answer + Citations (Ollama / OpenAI / Gemini)

Quick Start

Prerequisites

  • Python 3.10+
  • Node.js 18+ and npm
  • Ollama (for local LLM) — or OpenAI/Gemini API key

Step 1: Clone and Install Backend

git clone https://github.com/your-username/DocuMentor.git
cd DocuMentor
pip install -r requirements.txt

Step 2: Install Frontend

cd frontend
npm install
cd ..

Step 3: Configure Environment

cp .env.example .env
# Edit .env with your settings (see Configuration section below)

Step 4: Start Ollama (if using local LLM)

ollama pull gemma2:2b
ollama serve

Step 5: Launch Everything

python launcher.py

This starts both the FastAPI backend (port 8100) and Next.js frontend (port 3000).

You're running! Open http://localhost:3000 in your browser. Go to /dashboard to ingest documentation, then /qa to ask questions.

Data Layer Overview

The data/ directory is DocuMentor's knowledge base. It holds the catalog of available documentation sources, pre-processed documentation files, the vector database, and caches. Understanding this layer is key to understanding how information enters the system.

Document Catalog (data/doc_catalog.json)

This JSON file defines all available documentation sources. Each entry describes one documentation source that can be ingested into the system. Think of it as a "menu" of documentation that the system knows about.

Catalog Entry Structure

{
  "id": "python",                    // Unique identifier (used in API calls)
  "name": "Python Documentation",    // Display name in the UI
  "category": "Languages",           // Grouping category
  "icon": "python",                  // Icon name for the frontend
  "source_type": "preembedded_file", // How to fetch this documentation
  "source_paths": [                  // Where the content lives
    "data/preembedded/python_docs.txt"
  ]
}

Source Types Explained

1. preembedded_file

Plain text files stored in data/preembedded/. These are the simplest source type — just readable text that gets chunked and embedded directly.

  • Format: Plain .txt files with documentation content
  • Example: data/preembedded/python_docs.txt
  • Processing: Read file → chunk → embed → store
  • Best for: Documentation you've manually curated or downloaded

2. scraped_json

Pre-scraped documentation stored as JSON in data/scraped/. These were fetched from documentation websites and saved in a structured format.

  • Format: JSON files with title, url, and content fields
  • Example: data/scraped/react_docs.json
  • Processing: Parse JSON → extract content → chunk → embed → store
  • Best for: Documentation pre-scraped from websites

3. web_scrape

Live URL scraping. When a user adds a URL via the Dashboard, the system fetches the page content at ingest time using the Document Processor.

  • Added via: Dashboard "Add URL" form or POST /docs/custom API
  • Processing: Fetch URL → extract text → chunk → embed → store
  • Best for: Adding specific documentation pages or articles

4. file_upload

User-uploaded files (PDF, Markdown, TXT, HTML, etc.) stored in data/uploads/.

  • Added via: Dashboard file upload or POST /upload API
  • Supported formats: .txt, .md, .pdf, .html, .htm, .json, .csv, .xml, .yaml, .yml, .rst, .py, .js, .ts, .java, .go, .rs
  • Processing: Parse file → extract text → chunk → embed → store

Document Registry

File: rag_system/core/registry/registry.py (229 lines)

Models: rag_system/core/registry/models.py

The DocRegistry is the system's state manager. It tracks which documentation sources exist, which are ingested, and their current status. It is the single source of truth for document state.

Key Data Models

class IngestionStatus(str, Enum):
    NOT_STARTED = "not_started"   # Never been ingested
    IN_PROGRESS = "in_progress"   # Currently being ingested
    COMPLETED   = "completed"     # Successfully ingested
    FAILED      = "failed"        # Ingestion failed with error

class DocSourceType(str, Enum):
    PREEMBEDDED_FILE = "preembedded_file"  # .txt in data/preembedded/
    SCRAPED_JSON     = "scraped_json"      # .json in data/scraped/
    WEB_SCRAPE       = "web_scrape"        # Live URL fetch
    FILE_UPLOAD      = "file_upload"       # User-uploaded file

class DocSource(BaseModel):
    id: str                          # e.g., "python"
    name: str                        # e.g., "Python Documentation"
    category: str                    # e.g., "Languages"
    icon: str                        # e.g., "python"
    source_type: DocSourceType
    source_paths: List[str]          # File paths or URLs
    status: IngestionStatus          # Current state
    chunk_count: int = 0             # Chunks in vector store
    last_ingested: Optional[str]     # ISO timestamp
    error_message: Optional[str]     # Error if failed

How the Registry Works

  1. Initialization: Reads data/doc_catalog.json to load all available doc sources
  2. State persistence: Saves runtime state (status, chunk counts, errors) to data/registry_state.json
  3. State merge: On startup, merges catalog entries with saved state (so ingested sources stay marked as "completed")
  4. Dynamic additions: New sources added via URL or upload get appended to the registry at runtime

Smart Chunker

File: rag_system/core/chunking/chunker.py (375 lines)

The SmartChunker splits long documents into smaller, semantically meaningful chunks. This is crucial because:

  • Embedding models work best with focused text segments (not entire documents)
  • Retrieved chunks need to be small enough to fit in the LLM's context window
  • Smaller chunks give more precise search results

Chunking Strategy

The chunker uses a hierarchical splitting approach:

  1. Code block detection: First, identify fenced code blocks (``` ... ```) and protect them from being split mid-block
  2. Header-based splitting: Split on Markdown headers (# , ## , ### ) to preserve logical sections
  3. Paragraph splitting: Within sections, split on double newlines (paragraph boundaries)
  4. Sentence splitting: If paragraphs are still too large, split on sentence boundaries
  5. Hard splitting: As a last resort, split on word boundaries at the token limit

Configuration

ParameterDefaultMeaning
chunk_size500 tokensTarget maximum tokens per chunk
chunk_overlap50 tokensTokens of overlap between consecutive chunks (for context continuity)

Chunk Metadata

Every chunk produced by the SmartChunker includes metadata:

{
  "technology": "python",              // Doc source ID (critical for filtering)
  "source": "Python Documentation",   // Human-readable source name
  "chunk_index": 0,                   // Position in the document
  "total_chunks": 42                  // Total chunks from this document
}
Important Convention: All chunks must include technology metadata set to the doc source ID. This is how the vector store filters search results by technology. Without it, technology-specific search will not work.

Vector Store (ChromaDB)

File: rag_system/core/retrieval/vector_store.py (~400 lines)

The ChromaVectorStore wraps ChromaDB to provide persistent vector storage and similarity search. It converts text chunks into 384-dimensional vectors using the all-MiniLM-L6-v2 embedding model and stores them on disk.

How Embeddings Work

An embedding is a fixed-length vector of numbers that captures the meaning of a text. Similar texts produce vectors that are close together in vector space. When a user asks a question, we:

  1. Convert the question text into a 384-dimensional vector (using the same model)
  2. Search the database for stored vectors closest to the question vector (cosine similarity)
  3. Return the text chunks associated with those closest vectors

CachedEmbeddingFunction

The vector store uses a CachedEmbeddingFunction that wraps sentence-transformers. It caches computed embeddings to data/embeddings_cache/ so re-ingesting the same text doesn't recompute embeddings (saves time on startup).

ChromaDB Filter Pattern

When searching for technology-specific results:

# Search only in Python documentation
results = vector_store.search(
    query="How do list comprehensions work?",
    k=5,
    filter={"technology": "python"}
)

Corrupted Database Recovery

ChromaDB's SQLite-based storage can occasionally become corrupted (e.g., after a crash). The vector store includes automatic recovery:

  1. On initialization, attempt to create a PersistentClient
  2. If it fails with a database error, log a warning
  3. Delete the corrupted data/chromadb/ directory
  4. Create a fresh PersistentClient (data will need re-ingestion)
try:
    self._client = chromadb.PersistentClient(path=self._persist_dir)
except Exception as e:
    logger.warning(f"ChromaDB corrupted, resetting: {e}")
    shutil.rmtree(self._persist_dir, ignore_errors=True)
    self._client = chromadb.PersistentClient(path=self._persist_dir)

Ingestion Pipeline

File: rag_system/core/ingestion/pipeline.py (315 lines)

The IngestionPipeline is the orchestrator that ties all the pieces together. When you click "Add" on a documentation source in the Dashboard, this is the class that runs the end-to-end process.

Ingestion Flow (step by step)

  1. Receive request: API endpoint calls pipeline.ingest(doc_id)
  2. Look up source: Registry provides the DocSource with type and paths
  3. Update status: Registry status → in_progress
  4. Fetch content: Based on source_type:
    • preembedded_file: Read .txt file from disk
    • scraped_json: Parse .json file from disk
    • web_scrape: Fetch URL via document processor
    • file_upload: Read uploaded file via document processor
  5. Chunk content: Pass text to SmartChunker.chunk_document()
  6. Clean old data: Delete any existing chunks for this doc_id from vector store
  7. Embed & store: Pass chunks to VectorStore.add_documents()
  8. Update registry: Status → completed, set chunk_count and timestamp
  9. Handle errors: If anything fails, status → failed with error message

Progress Tracking

The pipeline tracks progress (percentage complete) during ingestion. The frontend polls GET /docs/{id}/progress every 1.5 seconds to show a progress indicator.

Async Design

The ingest() method is async. When triggered via the API, it runs as a background task using FastAPI's BackgroundTasks, so the API response returns immediately and ingestion proceeds asynchronously.

Important: Use SmartChunker.chunk_document() (singular) in async contexts, not chunk_documents(). The singular method is the async-compatible version.

LLM Handler (Multi-Provider)

File: rag_system/core/generation/llm_handler.py (311 lines)

The EnhancedLLMHandler is the component that generates answers. It supports three LLM providers and can switch between them at runtime.

Supported Providers

ProviderDefault ModelRequirementsBest For
Ollamagemma2:2bOllama running locallyFree, private, no API key needed
OpenAIgpt-3.5-turboOPENAI_API_KEYHigh quality answers
Geminigemini-proGEMINI_API_KEYGoogle's LLM alternative

How Answer Generation Works

  1. Receive question + retrieved chunks from the vector store
  2. Build prompt: System prompt instructs the LLM to answer based on provided context
  3. Inject context: Retrieved chunks are formatted and inserted into the prompt
  4. Call LLM: Send the prompt to the active provider
  5. Parse response: Extract the answer text
  6. Attach citations: Include the source chunks used

Response Modes

The LLM handler supports different response modes that alter the system prompt:

  • Smart Answer: Concise, direct answer with key points
  • Code Generation: Focus on producing working code examples
  • Detailed Sources: Verbose answer with extensive source citations

Provider Switching

Users can switch providers at runtime via the Q&A settings sidebar or the POST /providers/switch API endpoint. The handler validates the provider name and reconfigures the underlying LLM client.

Web Search Augmentation

The WebSearchProvider optionally augments RAG answers with live web results. When enabled, it searches the web for the user's question and includes relevant results as additional context alongside the vector store results.

Backend API (FastAPI)

File: rag_system/api/server.py (~666 lines)

The FastAPI backend exposes 17 REST endpoints that the frontend (and any external client) uses. It runs on port 8100 with CORS configured for the Next.js dev server at http://localhost:3000.

App Factory Pattern

The FastAPI app uses a factory pattern with deferred imports. Heavy dependencies (ChromaDB, sentence-transformers, etc.) are only imported when create_enhanced_fastapi_app() is called, not at module import time. 

# rag_system/api/server.py
_app = None

def create_enhanced_fastapi_app():
    global _app
    if _app is not None:
        return _app

    # Heavy imports happen HERE, not at module top
    from rag_system.core.retrieval import VectorStore

Lazy Import Pattern

DocuMentor uses a lazy import pattern in its core module to avoid heavy import-time side effects. Without this, simply importing rag_system.core would trigger ChromaDB initialization, download embedding models, etc.

How It Works

The rag_system/core/__init__.py file uses Python's __getattr__ hook. Attributes are only imported when first accessed: 

# rag_system/core/__init__.py

_LAZY_IMPORTS = {
    "SmartChunker": "rag_system.core.chunking",
    "ChromaVectorStore": "rag_system.core.retrieval.vector_store",
    "VectorStore": "rag_system.core.retrieval.vector_store",
    # ... etc.
}

def __getattr__(name):
    if name in _LAZY_IMPORTS:
        module = importlib.import_module(_LAZY_IMPORTS[name])
        attr = getattr(module, name)
        globals()[name] = attr    # Cache for next access
        return attr
    raise AttributeError(f"module 'rag_system.core' has no attribute '{name}'")

Why This Matters

  • Fast imports: import rag_system is near-instant
  • Test-friendly: Tests can mock modules before they're imported
  • Selective loading: Only used components are initialized
Testing Note: When mocking these lazy imports in tests, you must patch at the subpackage re-export level, not the source module level. For example, patch rag_system.core.retrieval.VectorStore, not rag_system.core.retrieval.vector_store.ChromaVectorStore.

Caching System

DocuMentor implements two layers of caching:

1. Embedding Cache

Stored in data/embeddings_cache/. The CachedEmbeddingFunction in the vector store caches computed embeddings keyed by text content hash. Re-ingesting unchanged text reuses cached embeddings.

2. Response Cache

Stored in data/cache/. LLM responses can be cached keyed by the question + settings combination. This avoids redundant LLM API calls for identical questions.

Troubleshooting

Common Issues

ChromaDB: "database disk image is malformed"

This means the SQLite database used by ChromaDB got corrupted. The system handles this automatically by deleting and recreating the database. If the automatic recovery doesn't work: 

# Delete the ChromaDB directory manually
rm -rf data/chromadb/

# Re-ingest your documentation
# (use the Dashboard or API to trigger ingestion for each source)

Ollama connection refused

Make sure Ollama is running:

ollama serve
# In another terminal, verify:
curl http://localhost:11434/api/tags

Frontend can't reach backend (CORS error)

Ensure the FastAPI backend is running on port 8100 and that http://localhost:3000 is in the CORS allowed origins list in rag_system/config/settings.py.

Embedding model download takes too long

The first time the system runs, it downloads the all-MiniLM-L6-v2 model (~80MB). This is a one-time download. Subsequent starts use the cached model.

Tests fail with "module has no attribute" errors

This usually means test patches are targeting the wrong module path. Due to the lazy import pattern, patches must target the re-exported names: 

# CORRECT
patch("rag_system.core.retrieval.VectorStore", ...)
patch("rag_system.core.chunking.SmartChunker", ...)

# WRONG (these names don't exist on the package namespace)
patch("rag_system.core.retrieval.ChromaVectorStore", ...)
patch("rag_system.core.retrieval.vector_store.ChromaVectorStore", ...)

Port already in use

# Find and kill the process using port 8100 (Linux/Mac)
lsof -i :8100
kill -9 <PID>

# On Windows
netstat -ano | findstr :8100
taskkill /PID <PID> /F
